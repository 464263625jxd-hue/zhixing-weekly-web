## 📁 文件结构

前端部署后从根目录加载 `data.json`（含 `issueIds`、`_meta`），再按需请求 `issues/issue<N>.json` 各期正文，并轮询 `version.json` 判断是否有新版本。
仓库中提交 `data.source.json`、`data.json` 与 `version.json`；其中 `data.json` 和 `version.json` 由部署前脚本生成，提交前不要手工编辑。

```
WeeklyWeb/
├── data.source.json       # 源数据：companies、静态元信息（提交到 Git）
├── data.json              # 部署产物：主索引（由脚本生成，提交到 Git）
├── index.html             # 单页应用入口
├── favicon.svg            # 网站图标
├── version.json           # 部署产物：版本信息（由脚本生成，提交到 Git）
├── README.md              # 本文件
│
├── issues/                # 各期完整数据（扁平 JSON）
│   ├── issue61.json
│   └── …                  # issue62.json … issue78.json
│
├── liveRadar/             # 频道快讯数据，首页实时情报入口读取
│   └── latest.json
│
├── js/                    # 本地托管的前端脚本（UMD 等）
│   └── zechariah-tracking.umd.js
│
├── docs/                  # 文档与规范
│   ├── FILE_MANAGEMENT.md   # 文件管理规范 ⭐
│   ├── STANDARDIZATION.md
│   ├── WORKFLOW_v2.md
│   ├── TRACKING.md
│   └── …
│              
└── scripts/
        └── sync-data-from-issues-data.py  # 根据 data.source.json + issues/ 生成部署文件
```

**📖 [文件管理规范](docs/FILE_MANAGEMENT.md)** - 每次更新必读！

部署前在仓库根目录执行：

`python3 scripts/sync-data-from-issues-data.py`

发布前质量检查：

```bash
# 检查最新一期
python3 scripts/check-weekly-quality.py issues/issue78.json

# 检查全部历史期
python3 scripts/check-weekly-quality.py
```

典型部署流程：

```bash
git pull
python3 scripts/check-weekly-quality.py issues/issue78.json
python3 scripts/sync-data-from-issues-data.py
# 然后由运维同步/发布静态文件
```

发布前如更新了 `issues/issue<N>.json` 或 `data.source.json`，必须重新执行同步脚本，并将更新后的 `data.json`、`version.json` 一并提交。

### 单条资讯字段规范

必需字段：

| 字段 | 说明 |
|------|------|
| `id` | 单期内唯一编号 |
| `category` | 只能使用 8 个固定板块：宏观、平台、跨境、数码科技、美妆、母婴、食品饮料、宠物 |
| `subCategory` | 板块下的细分主题，不应与 `category` 同名 |
| `title` | 资讯标题 |
| `content` | 详情正文 |
| `highlight` | 本期头条标记，每期应只有 1 条 |
| `isAlert` | 预警资讯标记，仅用于风险/异常/监管/价格/渠道/供应链/竞争冲击等需要提前关注的资讯；当期每个已发布板块至少保留 1 条 |

推荐字段：

| 字段 | 说明 |
|------|------|
| `summary` | 可选列表短摘要；只有明显短于 `content` 且不重复时填写，缺失时前端会显示正文片段 |
| `tags` | 资讯标签 |
| `sourceTitle` | 来源名称，如 Foodaily、母婴行业观察、Mysteel |
| `sourceUrl` | 原文链接；同一来源拆多条时可复用 |
| `sourceDate` | 原文发布日期或覆盖周期，无法确认时留空，不要编造 |

前端详情页会优先显示 `sourceTitle/sourceName/source`，有 `sourceUrl/url` 时展示“查看原文”。新期制作应尽量补齐来源链接，方便复核。

### v1.10.4 (2026-05-25) - 首页导读与预警覆盖优化

**前端体验**:
- 优化首页“本期赛道导读”布局，改为可读卡片展示，避免 8 个过窄竖条导致标题和摘要难以阅读。
- 首页导读每个板块同时展示重点资讯和预警资讯，摘要统一截断为短摘录，避免完整正文撑开卡片。
- 行业入口进入后立即加载往期资讯，并将重点/预警资讯打标后置顶显示。

**数据与规则**:
- 补齐历史各期已发布板块的预警覆盖，保证每个板块至少 1 条预警资讯。
- 明确重点资讯与预警资讯分离，避免同一条资讯重复承担两个展示位。
- 更新本地 `zhixing-weekly` skill：固化首页导读可读布局、板块预警覆盖、行业历史加载和摘录显示规则。

### v1.10.3 (2026-05-25) - 历史数据质量修复与摘要单源规则

**数据质量**:
- 清理历史期条目级 `summary` 与 `content` 完全重复的问题，`content` 保持为详情正文单一来源。
- 补齐历史期 `summary/content` 句末标点，避免前端显示截断句。
- 修复旧期多个 `highlight`、`isAlert` 数量异常、`零售` 旧分类、缺失洞察和重复标题等遗留质量问题。

**前端与规则**:
- 前端资讯卡片统一通过正文摘录函数展示摘要，缺少独立 `summary` 时自动回退到 `content`。
- 首页本期赛道导读、阅读页预警/重点资讯、行业页、企业页和全局搜索结果统一为“标题 + 正文摘录”展示。
- 赛道代表资讯不再以是否存在 `summary` 作为选择条件。
- 质量检查脚本将 `summary == content` 作为错误拦截，并区分历史期缺来源链接等非阻断信息。

### v1.10.2 (2026-05-22) - 双来源快讯与加载性能优化

**前端体验**:
- 频道快讯新增来源切换，当前支持“亿邦动力”和“36氪”两个来源，每个来源下再展示各自的二级频道。

**数据与流程**:
